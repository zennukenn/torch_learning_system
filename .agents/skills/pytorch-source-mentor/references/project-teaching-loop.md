# Project-integrated teaching loop

Use this reference for every substantive MiniTorch learning session. It exists
to prevent a project curriculum from degrading into a sequence of oral quizzes.

## Required microcycle

Run the session as short repeated cycles:

1. **Locate:** place the next behavior in the stable inference and repository
   map; state the observable MiniTorch outcome.
2. **Teach:** explain only the architecture language build or source concept
   needed for the next learner action. A teaching block normally lasts 10-20
   minutes before a repository action.
3. **Build:** the learner immediately authors or materially changes one design
   artifact configuration source file or test. Inspect the real MiniTorch diff.
4. **Verify:** ask for one expected result then run the narrowest relevant
   command. Preserve actual output and evidence limitations.
5. **Debug:** use a real failure when available. The learner states a hypothesis;
   the mentor instruments and narrows it without replacing learner reasoning.
6. **Compare:** inspect one pinned PyTorch responsibility corresponding to the
   implemented layer and record one simplification or scaling consequence.
7. **Defend briefly:** at the end the learner explains the diff path evidence and
   remaining limitation. Convert important gaps into a code test source lookup
   or delayed repair whenever possible.

The full session may keep the learner's preferred explanation/practice/source
ratio but must interleave it across these cycles. Do not deliver the entire
lecture first and defer all project work to the end.

## Question budget and stop rule

- Use one opening diagnostic set with at most three short questions. Do not
  restart diagnostic questioning after each partial answer.
- Comprehension checks inside teaching concern material just taught and lead
  directly to an edit command test or source observation.
- One compact end-of-session defense is allowed. Ask at most three focused
  follow-ups across the whole gap audit.
- If two consecutive oral repairs target the same gap stop asking. Mark the gap
  and create a concrete MiniTorch change test or experiment that exposes it.
- An incomplete oral answer changes scaffolding and hint level; it does not by
  itself block a safe learner project action.

## Authorship boundary

Learner-owned evidence includes commands design text code configuration and
tests written by the learner and visible in the MiniTorch diff or session
artifact. The mentor may explain prerequisites define interfaces prepare an
empty or mechanical scaffold add instrumentation and run commands.

The mentor must not pre-create the artifact that the lesson is intended to
teach. If mentor work already exists label every affected file as a mentor draft;
the learner must review and materially revise or replace it before it can become
learner evidence. Merely approving the draft or repeating its contents does not
change provenance.

## Evidence boundary

A completed project session records at least one teaching-to-practice cycle one
learner-authored artifact or diff one focused verification and one PyTorch
source comparison. Runtime/debug/modify scores require the corresponding real
execution authorship and hypothesis evidence. A design-only increment may score
explanation or location but still requires a learner-authored repository
artifact rather than chat-only answers.
